# Changelog

## 1.0.9

- **Оригинальная иконка приложения А.М.Видео с логотипом Home Assistant
  в правом нижнем углу.** Файлы `brand/` (icon/logo, @2x, тёмные варианты)
  с HA 2026.3 автоматически показываются в «Настройки → Устройства и
  сервисы», а иконка сущностей (кнопка, шлагбаум, камера) видна в
  more-info и на Tile-карточках (`entity_picture`).
- **Локальный рестрим видео для NVR — новый режим для Frigate.** В
  параметрах появился переключатель «Локальный рестрим видео для NVR
  (Frigate)». После включения камера раздаёт живое видео по локальному
  адресу `http://homeassistant:8123/api/amvideo/restream/<запись>/<КПУ>.mjpg?token=…`
  (без авторизации HA, доступ защищён случайным токеном, рестрим по
  умолчанию выключен). Готовый адрес для `config.yml` Frigate показывается
  в атрибутах камеры (`frigate_input`) — облако А.М.Видео отдаёт видео
  только через WSS-прокси, Frigate такое не читает напрямую.
- Основа для автооткрытия шлагбаума по распознаванию машины: подробности
  в репозитории [ha-smart-access](https://github.com/NoIDXMV6/ha-smart-access).

## 1.0.8

- **Исправлено «ValueError: invalid literal for int()»: сервер А.М.Видео
  сменил протокол видеопорта.** `type=video` теперь возвращает не номер
  порта, а строку **«порт/одноразовый-токен»** (реальный пример:
  `7077/KFVyuAbAeS`), а поток живёт на `wss://stream.amvideo-msk.ru:7077/
  <токен>`. Раньше интеграция делала `int("7077/KFVyuAbAeS")` и падала —
  камера не показывала ничего. Поддержаны оба формата: новый
  `порт/токен` и старый `порт`, а также полный URL, если сервер пришлёт
  его целиком.
- Атрибуты камеры дополнены диагностикой последней попытки:
  `video_port` (порт без токена), `frames_seen`, `last_error`.
- Тесты обновлены под протокол 2026 (мок-сервер отдаёт цель
  `порт/токен`), добавлены проверки сборки URL в обоих форматах.

## 1.0.7

- **Исправлено «камера не показывает видео» (главная причина).** TLS
  видеопрокси `wss://stream.amvideo-msk.ru:<порт>` теперь **не
  проверяется** (ssl=False, как в приложении А.М.Видео). Сертификат,
  который отдаёт видеопрокси, выпущен на `unity-nvr.amvideo-msk.ru` и не
  покрывает имя `stream.amvideo-msk.ru` (проверено openssl, ноябрь 2026):
  aiohttp с проверкой по умолчанию разрывал соединение **до первого
  байта видео** — окно камеры пустело без единой ошибки. Отключить
  проверку можно было и раньше приложением — теперь и интеграция ведёт
  себя так же (опция `stream_ssl_verify`, по умолчанию выкл.).
- **Watchdog первого кадра.** Если WebSocket подключился, но сервер не
  передаёт данных дольше 25 с — попытка рвётся с понятным WARNING
  `сервер не передаёт видеоданные` и переподключением. Раньше такой
  поток висел молча: пустое окно без единой записи в журнале.
- **Ошибки API больше не теряются.** «Камера недоступна (сервер не выдал
  порт)» и «нет доступа» при запросе `type=video` попадают в журнал как
  WARNING (раньше умирали на DEBUG-уровне); обрыв MJPEG-потока пишется в
  журнал всегда, а не только в debug-режиме.
- **Атрибуты самодиагностики камеры:** `ffmpeg_available`,
  `stream_host`, `stream_tls_verify`.
- Новые тесты `scripts/test_stream_v107.py`: мок-wss с самоподписанным
  сертификатом (все 5 сценариев), регресс-тесты api/stream — без
  изменений (13 проверок), e2e на HA 2025.1 — без изменений.

## 1.0.6

- **Пустое окно камеры теперь объясняется в журнале.** Каждая неудача
  снимка или потока (ffmpeg не найден, сервер не выдал видеопорт,
  WebSocket отклонён, лимит попыток исчерпан) пишется в журнал HA как
  WARNING — не чаще одного раза в 5 минут на каждую причину, без спама.
- `ffmpeg_available()` теперь проверяется на каждый вызов, а не один раз
  при старте HA (после установки ffmpeg перезапуск HA больше не нужен).
- Локальный e2e-тест камеры приведён к текущей модели сессий (sid в
  записи конфигурации), прогнан на реальном HA 2025.1: снимок через
  WebSocket → ffmpeg → JPEG проходит полностью.

## 1.0.5

- **Иконки бренда в составе интеграции.** Начиная с Home Assistant 2026.3

  проходит полностью, без отключённых проверок (условие включения в

## 1.0.4

- **Исправлена ошибка `already_in_progress` при добавлении интеграции.**
  Незавершённая попытка настройки (закрыли окно с PIN, код не пришёл,
  лимит «3 ПИН в сутки», рестарт HA посреди настройки) оставалась «в
  работе» и пережила бы любой рестарт Home Assistant — а каждая новая
  попытка добавления обрывалась сообщением `already_in_progress`. Теперь
  при старте настройки интеграция сама прерывает зависшие попытки того
  же аккаунта, и мастер запускается заново в любом случае.
- Если аккаунт успели настроить из другого окна, пока ждали SMS-код, —
  вторая запись не создаётся (мастер закроется с «Этот аккаунт уже
  добавлен»).
- На случай гонки с другим окном добавлен человекочитаемый перевод
  abort-причины `already_in_progress`.

## 1.0.3

- **Сессия приложения на телефоне больше не слетает при работе
  интеграции.** Сервер А.М.Видео держит одну активную сессию на аккаунт:
  каждый повторный `type=login` завершал сессию приложения — а интеграция
  логинилась заново при каждом рестарте Home Assistant. Теперь `sid`
  сохраняется в записи конфигурации и переиспользуется: после рестарта HA
  вход не повторяется, приложение продолжает работать.
- Keep-alive сессии `type=auth` раз в 55 минут — ровно как в приложении
  (оно продлевает сессию раз в час активности). Опрос `type=panels`
  продолжает работать как раньше.
- **Повторная авторизация из настроек.** Автологин убран совсем: если
  сервер ответил «нет доступа» (сессию перехватил свежий вход в
  приложении или истёк срок), интеграция поднимает reauth — HA показывает
  «Требуется повторная авторизация», удалять и добавлять интеграцию не
  нужно. Автовход отключён специально: он завершал бы сессию приложения
  (получился бы вечный цикл «интеграция ⇄ приложение»).
- В настройках интеграции (Настройки → А.М.Видео → ⚙) появилось меню:
  «Параметры опроса и таймингов» и «**Повторная авторизация (новый
  вход)**» — запускает reauth вручную в любой момент.
- Список КПУ, команды открытия и видео работают по сохранённой сессии
  без изменений.

## 1.0.2

- Мастер настройки переделан по сценарию приложения: шаг 1 — телефон и
  пароль; при требовании PIN интеграция **сама высылает код по SMS**
  (type=pin, pin_type=device, sms=0 — как первое нажатие «Запросить ПИН»),
  затем пользователь вводит код на отдельном шаге.
- Поле device_key убрано из формы: генерируется и хранится автоматически,
  повторные входы идут без PIN.
- Повторная высылка PIN вынесена в галочку на шаге ввода кода (sms=1,
  как повторное нажатие кнопки в приложении) и больше не выполняет вход
  в том же запросе.
- Reauth тоже автоматом высылает PIN: при требовании PIN больше не нужно
  запрашивать код вручную.
- Если сервер снова затребует PIN при работе (забыл устройство) —
  координатор поднимает reauth вместо вечного UpdateFailed.

## 1.0.1

- Исправлен запрос PIN: в приложении кнопка «Выслать PIN» шлёт
  `pin_type=device` (не `login`) — теперь интеграция делает так же.
- Запрос PIN и вход разделены на два шага (как в приложении): новый PIN

- Все ошибки входа/PIN сопровождаются текстом от сервера.
